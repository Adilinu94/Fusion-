## 1. Was ist das Projekt?

**FlowRep / DropSync** ist eine komplett lokale Android-App (kein Konto,
keine Analytics, kein Netzwerk) mit drei Säulen:

1. **Musikplayer** (DropSync-Teil): Media3-basiert, eigene DSP-Kette,
   Marker auf der Waveform, Crossfade, Drop-Landung
2. **Krafttrainingstagebuch**: flaches Satz-Log, Übungen, PR-Berechnung,
   Fortschritts-Charts
3. **Fusion (FlowRep-Teil):** BLE-Sensor (Gyro/Accel) zählt
   Wiederholungen live, DropSync landet Musik-Drops exakt am
   Satzende (Rest-Pausen mit Musiktiming)

**Sichtbarer App-Name:** FlowRep. **Paketname:** `com.dropsync` (aus
Kontinuitätsgründen beibehalten).

**Zahlen:**
- 39 Gradle-Module (1 app, 5 core, 8 data, 8 domain, 6 feature, tools)
- 317 Kotlin-Quelldateien, 73 Testdateien
- Room-DB Version 6 (Migrationen 1→6 alle getestet)
- 14 ADRs in `docs/adr/`
- minSdk 26, compileSdk/targetSdk 37, JDK 17, Kotlin 2.4.10, AGP 9.3.1,
  Media3 1.10.1, Compose BOM 2026.06.01, Room 2.8.4, Hilt 2.60.1

:domain:library      Song/Marker/Playlist-Domain, SmartShuffle
:domain:playback     AudioClock, AudioRouteProfile, AudioTimestampExtrapolator

                     RepCounter, TemplateMatcher, OrientationTracker (Madgwick)

## 6. Schwachstellen-Einschätzung (meine ehrliche Analyse)

### Strukturell riskant

**a) Fast alles ist "codeseitig abgeschlossen", fast nichts
geräteverifiziert.** Das größte Risiko des Projekts. Die Latenz-Werte
sind Tabellen-Schätzungen, die Rep-Zählung lief nur gegen synthetische
und fremde Datensätze, Waveform-FPS nie instrumentiert. Ein Review
sollte prüfen, ob die 5 Freigabe-Szenarien wirklich der kritische Pfad
sind und ob sie vor Release durchführbar sind.

**b) Die Shadow-Pipeline zählt live (ADR-0014), aber ohne
Hardware-Freigabe.** Die Flags für Accel/Orientation sind aus, aber der
Gyro-Live-Pfad ist der Kern der App. Falls die Freigabe-Szenarien
fehlschlagen, steht das zentrale Feature ohne Fallback da. Es gibt
keinen abgesicherten "manuellen Modus" als Plan B.

**c) BT-Codec-Erkennung per Reflection.** `getBluetoothCodecStatus()`
ist versteckte API; der Aufruf kann auf jedem Gerät/Android-Update
anders reagieren. Es gibt keinen Test dafür (nur on-device möglich).
Die Fallback-Kette (null → SBC) ist korrekt, aber die AAC/LDAC-Werte
sind weiterhin Schätzungen, keine Messungen.

### Architektonische Beobachtungen

**d) `TrainViewModel` trägt viel Verantwortung.** Live-Engine +
Shadow-Engine + Recorder-Sessions + BLE-Lifecycle + Satz-Logging in
einem ViewModel. Die Testbarkeit ist gegeben (Fakes), aber die
Kohäsion könnte besser sein (z. B. ein eigener Engine-Host-UseCase).

**e) Viele parallele Doku-Ebenen.** 8 Ausbaupläne im Root, 7 Design-Docs,
14 ADRs, STATUS_FORTSCHRITT. Es gab bereits zwei Doku-Kollisionen
(Abschnitt 9, Abschnitt 11b). Der doku_links_check verhindert
Umnummerierungs-Regressionen, aber kein Werkzeug erkennt inhaltliche
Widersprüche zwischen den Plänen (z. B. steht im README "Schritt 13
offen", während Teile davon implementiert sind).

**f) Domain-/Data-Grenze beim Sensor ist sauber, aber die
Calibration-Daten fließen über mehrere Pfade:** Profil (DataStore) →
TrainViewModel → Engine-Config. Bei jedem neuen Parameter (zuletzt
expectedDurationSamples) muss die Durchreichung an 3+ Stellen ergänzt
werden. Ein Config-Objekt statt einzelner Parameter würde das
verhindern.

### Performance-Beobachtungen

**g) Die Library beobachtet pro Song die Analyse** (`waveformFor`),
bei 1000+ Songs in der Liste entstehen 1000+ Flow-Subscriptions. Bisher
kein Messpunkt; LazyList sollte das abfangen, aber ein Review könnte
hier einen echten Stresstest fordern.

**h) Der Positions-Ticker läuft bei sichtbarem Now-Playing alle 200ms**
(`snapshotNow()`). Zusammen mit der Waveform-Neuzeichnung pro Frame
könnte das auf schwachen Geräten messbar sein. Strukturell unkritisch
(256 drawRoundRect), aber nie gemessen.

**i) Der Batch-Import fix ist drin (1 Query statt N), aber der
Erst-Scan einer großen Bibliothek erzeugt immer noch N Worker-Enqueues
(einzeln, über enqueueUniqueWork). WorkManager fasst die intern
zusammen, aber ein echtes 1000-Song-Import-Profil fehlt.**

### Test-Beobachtungen

**j) Kein einziger instrumentierter Test.** AudioFocus, Underruns,
MediaSession-Timing, BLE-GATT-Verhalten sind nur per Robolectric/Fakes
abgedeckt. Die BLE-GATT-Queue (serielle Queue, Timeouts) ist die
komplexeste Infrastruktur im Projekt und läuft nur gegen Fakes.

**k) Der Isolationstest der Pipeline nutzt einen synthetischen
Dreiecks-Stream.** Die ursprüngliche "Python-Verifikation" hatte die
Pending-Logik nicht nachgebildet (in Abschnitt G dokumentiert). Das
zeigt: die Zähl-Pipeline hat genug versteckte Zustände, dass man sie
leicht falsch testet. Ein Property-Based-Test (zufällige Streams gegen
invariante Eigenschaften) wäre robuster als handgebastelte Streams.

### Doku-/Prozess-Beobachtungen

**l) Die Regel "STATUS_FORTSCHRITT bei jeder Session aktualisieren"
wurde mehrfach verletzt** (Abschnitte C/D nachgetragen). Das Risiko
paralleler Sessions ist real (bereits 2 Kollisionen). Ein Review könnte
prüfen, ob der Handoff-Prozess vereinfacht werden kann (z. B. ein
automatisch generierter Stand aus Git-Log + STATUS).

## 8. Build, Test, Gotchas

**Kommandos:**
```
./gradlew test               # alle JVM-/Robolectric-Tests
./gradlew spotlessCheck      # Formatierung
./gradlew assembleDebug      # Debug-APK
python tools/shadow_harness.py --smoke-test
python tools/doku_links_check.py   # läuft auch in CI
```

**Gotchas (wichtig für jeden, der baut):**
- **JDK 17 zwingend** (nicht 25): SDK 36+/Robolectric fordern sonst
  Java 21. Lokal: `C:\Program Files\Eclipse Adoptium\jdk-17...` (die
  Junction `C:\dev\jbr17` zeigt inzwischen auf Temurin 17, nicht mehr
  auf Android-Studio-JBR).
- **Robolectric SDK 34** in `robolectric.properties` (core:database,
  data:audio, data:playback) - nicht hochziehen, solange JDK 17.
- **Gradle 9.5 Windows-Bug:** `-Djava.library.path` mit Leerzeichen
  zerreißt das Argument. Fix liegt in `feature/workout/build.gradle.kts`
  (minimaler Worker-PATH). Bei neuen Modulen mit Ticker/Log beachten.
- **CI:** GitHub Actions (test + doku_links_check + spotlessCheck +
  assembleDebug), nur auf master/fusion/**. Keine instrumentierten Tests
  in CI.
- **FFmpeg:** `-Pdropsync.enableFfmpeg=true` nur mit vorhandenem
  `libs/media3-ffmpeg`-Modul + NDK r28+.
- **Vor jedem Push:** `git fetch && git rebase origin/master`
  (Parallelarbeit hat schon zweimal kollidiert).
- **Kein `androidTest`-Verzeichnis existiert** - wer instrumentierte
  Tests anlegen will, startet bei Null (Testinfra-Plan Schritt 4).
- **Graphify-Index** war zuletzt stale; vor Graphify-Nutzung neu
  indexieren.

## 9. Vorschlag für die Review-Prioritäten

Die größte Hebelwirkung hat vermutlich (in dieser Reihenfolge):

1. **Prüfen, ob die 5 Freigabe-Szenarien (Gate 11b) überhaupt
   erreichbar sind** - wenn nein, braucht es einen Plan B für das
   Zähl-Feature.
2. **TrainViewModel-Komplexität und Sensor-Config-Durchreichung**
   (Schwachstelle d/f) - hier entsteht bei jeder Änderung Reibung.
3. **Library-Waveform-Subscriptions bei großen Bibliotheken**
   (Schwachstelle g) - potenzielle Skalierungsfalle.
4. **Instrumentierte Tests für die BLE-GATT-Queue und AudioFocus**
   (Schwachstelle j) - die risikoreichste ungetestete Infrastruktur.
5. **Doku-Konsistenz-Maschine** (Schwachstelle l) - ein automatisch
   generierter Projektstand würde die Parallelarbeit absichern.
